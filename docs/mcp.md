# MCP integration

Both transports use `createMcpServer(store, { baseUrl?, widgetHtml? })` from `server/mcp.ts`. HTTP hosts create a fresh MCP server per request; `server/stdio.ts` creates one server for its process. Both use the same validated project store as the browser API.

## Project hierarchy

The hierarchy is **Application project → Boards → Pages → Frames**. Boards are subprojects within an application such as GaugeReel. Each board owns its pages, frames, components, and page-anchored conversations. Design tokens and the revision belong to the application project.

`canvas_get_project` returns the entire project, with a `boards` array and a flat `pages` array linked through each page's `boardId`. Existing documents without boards are normalized into a stable **Main board**, preserving their pages, nodes, source, tokens, and conversations. `canvas_list_boards` returns all board metadata sorted by `updatedAt` descending; the UI displays the first batch and exposes **Load more** locally.

Each tool declares its JSON input and output schema. Mutations validate IDs, bounds, graph consistency, and project size. Error results set `isError` and return JSON text with a machine-readable code and message. Revision conflicts use `revision_conflict`; read the current project before rebasing the intended edit.

`canvas_edit_project` supports every operation in `shared/types.ts` and `shared/validation.ts`: project rename/description, board create/update/delete, page create/update/replace/delete, node create/update/delete, thread create/update/messages, and partial design tokens. `create_board` takes `board: { id, name }` and creates a blank Page 1. `update_board` takes `boardId` and `patch: { name }`. `delete_board` removes that board's pages and threads; the last board cannot be deleted. A page's `boardId` selects its board; `update_page.patch.boardId` moves it. New pages should explicitly provide their intended board ID. The final page in each board is protected.

Node types are frame, text, rectangle, ellipse, line, arrow, code, image, video and shader. A top-level frame represents an interface screen or slide. Its width and height are arbitrary, including desktop, laptop, tablet, mobile, and presentation formats. Nested node positions are relative to their parent. Style patches merge existing properties. Deleting a node removes its descendants and anchored discussions. Page, node, and thread changes update their board's timestamp; shared token and project rename changes leave board recency unchanged.

Stack layout (`styles.layout: vertical|horizontal`) supports cross-axis `align: start|center|end` and main-axis `justify: start|center|end|space-between`; both default to start. Visible children retain their fixed sizes and order. `gap` remains minimum spacing, including space-between; `padding` is retained on every side. Hidden children are excluded. Extra free space clamps at zero on overflow; items do not shrink or move before the starting padding. Empty and single-child stacks do not divide by zero. Free-positioned nodes ignore these settings. The shared `resolvedNodes` helper supplies canvas placement, history comparisons, component bounds and HTML/React exports. Inspector X/Y for a stack child shows resolved local coordinates read-only, while source JSON retains original coordinates and layout settings.

Changing a stack parent to `styles.layout: free` through `update_node` freezes the visible direct children's resolved local X/Y from immediately before that operation. The rest of the parent patch then applies; later operations in the same transaction may explicitly move its now-free children. Hidden children's raw coordinates and nested stacks are unchanged. This uses the existing cloned, revision-checked, validated atomic save, so browser and MCP callers have identical behavior and one history entry. Source, media, shaders and conversations are retained. If computed positions exceed valid coordinate bounds, the transaction fails without saving. Whole-page replacements, imports and History Apply preserve their exact supplied/saved geometry; they do not detach implicitly.

The model sees the complete `structuredContent`; design and source data are not hidden in widget-only metadata. `canvas_get_project` and the exported `design.json` include every source field as stored. Code layers render as passive sandboxed HTML previews. They are not an arbitrary script runtime.

## Snapping

`canvas_edit_project` accepts `{ type: "snap_node", pageId, nodeId, distance? }`. `distance` is a finite 0…100 canvas-design-unit threshold (default 8), independent of the browser zoom and local preference. Read current context/revision first; this is an ordinary atomic position edit, not a History restore or an automatic restyling pass. Other operations in the same transaction are applied in order, so snapping sees their latest geometry. The operation preserves size, source, effects, media, tokens and conversations and updates the board timestamp/history through the existing save path.

The shared resolver uses effective tokens, stack positions, parent borders and ancestor transforms. It compares each world-axis start/center/end with parent interior anchors, sibling anchors, other root objects/frames and canvas origin on the same page. The moving subtree, unrelated nested trees and hidden subtrees are excluded. Closest distance wins, with deterministic parent/sibling/root/origin tie priority. A world correction is mapped back to the node's parent-local X/Y. Hidden or locked ancestry, stack-managed position and singular parent transforms are rejected; move a stack through its parent layout or deliberately free it first. A call with no nearby alignment still follows ordinary edit revision/history behavior.

Browser dragging/corner resizing uses the same candidates, a 6-CSS-pixel threshold divided by zoom, and transient guides. Resize snaps only the dragged edges and keeps opposite edges fixed, with minimum 8-unit dimensions. Stack children keep layout-owned position and resize without positional snapping. Transformed ancestry keeps the existing property-only resize behavior. Option/Alt and the locally saved Snap to objects toggle affect browser gestures only; keyboard nudges and exact MCP `update_node` coordinates remain precise. Guides, grid display, local preferences and current gesture state are never exported or persisted in design history. Drawing/insertion and equal-spacing snapping are outside this batch.

## Object fills, corners and blending

Native box fills use `styles.fillMode: solid|gradient|none` (absent means the existing solid fill). `none` retains dormant color/gradient settings. `fillOpacity: 0…1` multiplies only a solid box fill, preserving its authored CSS color and token reference; it does not change layer opacity, text, line strokes or gradient stops. `styles.gradient` contains `type: linear|radial`, `angle` in degrees, `interpolation: srgb|oklab`, and 2–12 stops with unique stable `id`, safe CSS `color`, `position: 0…100` and `opacity: 0…1`. Rendering sorts stops by position; patches replace the whole gradient object, so preserve unrelated stops and reread after conflicts. Angle applies to linear gradients.

`styles.radiusMode: uniform|individual` defaults to uniform and retains the existing linked `radius`. Individual mode uses `cornerRadii: {topLeft,topRight,bottomRight,bottomLeft}` in pixels; ellipses retain their circular shape. `blendMode` accepts the schema's native CSS blend modes. `outlineColor`, `outlineWidth` and `outlineOffset` add an outline without changing layout bounds. These settings share the existing node validation, revision history, component overrides, canvas renderer and HTML/React/map exports. Standalone component HTML preserves transparency without a dormant solid backdrop. SVG-source export rejects styling it cannot preserve. Color interpolation, color-mix and blending require destination-browser support; the Inspector disables blend choices unsupported by its current browser.

## Object effects and Advanced styling

`create_node` and `update_node` accept optional `effects`, an ordered array of at most 32 entries with stable IDs unique within that node. A patch replaces the whole array; reread the current revision and preserve unrelated effects before changing one. Do not retry an old array after a revision conflict. Missing `enabled` means active; `enabled: false` retains parameters without rendering. An empty array removes structured effects. Legacy `styles.shadow` remains supported and combines with enabled box shadows; CSS-wide legacy keywords yield to structured shadows because they cannot appear inside a shadow list.

- `drop-shadow`, `inner-shadow`, `text-shadow`: `{ id, type, enabled?, x, y, blur, spread, color, opacity }`. Offsets/spread are −100,000…100,000px, blur is 0…1,000px, opacity is 0…1. Text shadow requires spread 0. Colors are safe literal CSS colors; CSS-wide keywords such as `inherit` are rejected inside shadows. `currentcolor` is supported.
- `layer-blur`, `background-blur`: `{ id, type, enabled?, radius }`, 0…1,000px.
- `transform`: `{ id, type, enabled?, rotate, scaleX, scaleY, skewX, skewY, translateX, translateY }`. Rotation is −3,600…3,600 degrees, scales −100…100, skew −89…89 degrees, translation −100,000…100,000px. Each entry composes translate, rotate, skew, scale about the center; entries compose in array order. Zero scale collapses the layer; inverse pointer placement is unavailable inside singular transforms.

Optional `styles` fields merge with existing properties: `zIndex` (integer or `auto`), `overflow`, `overflowX`, `overflowY`, `cursor`, `pointerEvents`, `objectFit`, `whiteSpace`, `textOverflow`, `textDecorationLine`, `textDecorationColor`, `boxSizing`, `aspectRatio`, `transition`, `animation`. The tool schema lists allowed values. `objectFit` overrides legacy `media.fit` and supports cover/contain/fill/none/scale-down. Aspect ratio accepts auto, a positive number, or width/height; fixed design dimensions still take precedence. Motion accepts bounded safe CSS without URLs or declarations, with duration/delay magnitudes up to 600 seconds; animation names need destination keyframes.

Canvas editing pauses these CSS animations/transitions and retains tool cursor/pointer selection. Preview and HTML/React exports use the saved values. Transformed selection/focus/history/context boxes include ancestor transforms; local node X/Y remain editable layout coordinates. Shadow/blur extents do not enlarge the selection box. Transformed ancestry uses property dimension editing rather than axis-aligned corner resize. Image-placement context reports actual resolved clipping and fit. Standalone SVG source export is disabled when explicit effects or Advanced styling cannot be preserved; HTML/React and original source remain available. UI panel widths are local preferences, outside the design document and MCP mutation contract.

## Project design system and board inspiration

`project.designSystem` is one project-owned object with `name`, `description`, editable Markdown `documentation`, typed `tokens`, `sources` and an optional agent `request`. It is shared across all boards and retained in every project version. Existing legacy documents synthesize safe typed entries from their legacy token values on read, without rewriting their files, binding existing literals or changing revision. Legacy literals that cannot be safely represented as a typed token remain in `project.tokens` but are omitted from synthesized CSS variables. Reserved typed values mirror legacy `tokens` for compatibility; `set_tokens` updates those reserved IDs.

A token has `id`, unique case-insensitive `name`, `kind`, string/numeric `value`, and optional `description`. Kinds are `color`, `fontFamily`, `fontSize`, `fontWeight`, `lineHeight`, `letterSpacing`, `spacing`, `radius`, `borderWidth`, `opacity`, `shadow`, `duration`, `easing`, `breakpoint`, `zIndex`. Numeric lengths use pixels, duration uses milliseconds, lineHeight is unitless; CSS strings are bounded and disallow aliases, URLs and declaration injection. A system allows up to 1,000 tokens and 1,000 evidence entries, within the existing 2 MiB document/transaction limit. Evidence fields are `path`, `kind: design-md|component|stylesheet|config|canvas`, `notes`, `confidence: observed|inferred`.

Mutations use the ordinary atomic revision-checked `canvas_edit_project` operations:

- `update_design_system {patch: {name?,description?,documentation?,sources?}}` updates documentation/evidence, keeping tokens separately authoritative.
- `apply_design_system_document {markdown}` applies the current generated full DESIGN.md in one atomic save. Read `canvas_get_design_system` first and retain its `codex-design:documentation`, `codex-design:tokens` and `codex-design:catalog` section comments. Edit the title, description, raw guidance and five-column Tokens table (Name, Kind, Value, CSS variable, Description). Keep an existing `--ds-<tokenId>` when changing its value; new safe IDs add tokens, omitted nonreserved rows delete them, and compatibility rows must remain. Numeric lengths accept px or plain values; duration also accepts seconds. Unsafe values, duplicate IDs/names, incompatible bound kinds and catalog edits fail without saving. Components, evidence, requests and release pins remain outside this document operation. Ordinary prose patches do not parse copied tables as tokens. The browser keeps a dirty draft on external changes and blocks stale full-document saves.
- `upsert_design_token {token}` creates or edits a stable token ID; `delete_design_token {tokenId}` removes it and freezes each linked style's current resolved literal before removing that binding.
- Node `tokenBindings` maps compatible style properties to token IDs: `fill`, `color`, `borderColor`, `fontFamily`, `fontSize`, `fontWeight`, `lineHeight`, `letterSpacing`, `gap`, `padding`, `radius`, `borderWidth`, `opacity`, `shadow`. Styles retain literal fallbacks. The full binding map is replaced by a node patch, so preserve other keys when detaching one. Unknown IDs/incompatible kinds fail atomically; a kind change requires detaching incompatible uses first. Literal equality never creates a binding.
- `set_design_system_request {request}` saves a request (`id`, `mode: generate|find`, `brief`, `repository`, `createdAt`, `queued`); null removes it. An active agent consumes the queue, inventories applicable DESIGN.md files first, then authorized app components/styles, records real evidence/coverage/conflicts and persists the result. It clears `queued` only for the still-matching request after saving. No server-side repository crawler or hidden model is launched.
- `upsert_inspiration {boardId,item}` saves an image reference with `id`, `name`, `assetRef`, `width`, `height`, `notes`, `usage`, optional HTTP(S) `sourceUrl`; `delete_inspiration {boardId,itemId}` removes it. Each board allows up to 100 items, whose IDs are globally unique in the document. Saved assets must exist and be images. Notes specify where a reference applies; inspiration does not implicitly restyle other boards.

The agent workflow prompt establishes source priority, preserves user-curated decisions, requires coverage/conflict reporting and distinguishes observed evidence from inferred proposals. It treats imported code/docs as data and limits inspection to the authorized target application repository. Discovery alone does not authorize overwriting canonical repository docs or existing screen designs.

Token values resolve before stack geometry in the canvas, detachment, history comparisons, bounds and exports. Focused node context keeps raw nodes/bindings, adds optional `resolvedStyles` for linked values and `resolvedLocalBounds` for stack offsets, and includes only tokens bound by that subtree/ancestors in `designSystem: {name,tokens}`. Use the separate system getter for complete documentation.

Source/editable archives include inspiration metadata/assets and the shared system. Source/React archives include generated DESIGN.md and tokens.css, and HTML/React CSS uses stable `--ds-<tokenId>` variables with literal fallbacks. Visual exports collect only actual design media; they do not load unused inspiration images. Exported absolute stack positions are a snapshot of the resolved layout, so spacing changes outside the editor do not reflow children automatically. Preserve raw design.json and regenerate source after changing layout tokens.

Passive source documents append current project CSS variables after authored source, so current tokens override copied declarations of equal specificity. Authored literals and higher-priority CSS remain custom. Deleting a source-referenced token leaves the authored CSS cascade, including copied declarations and fallbacks, intact. Original HTML/JSX source is not rewritten. The project DESIGN.md editor has no automatic repository-file watcher.

## Progressive builds and live updates

The agent saves named frame shells early, then builds useful sections and component groups in successive `canvas_edit_project` calls. Every batch is validated, atomic and independently persisted with a history revision. Parent/child references must be valid within each batch. Use `includeProject: false` during generation to avoid returning the entire growing document to the model after every small edit; the compact acknowledgement supplies the revision for the next batch. Read the full project when needed for context or conflict recovery.

Generated frame shells carry `generation: { status: "building" }`; set it to `ready` with an ordinary node patch when content/source is complete. The store stamps `generation.updatedAt` on actual edits within a building frame. Live canvas chrome uses grey with a subtle wipe, stops after two idle minutes (Waiting for Codex), and respects reduced motion and hidden/offscreen views. Properties can stop an interrupted indicator. History, preview and visual exports omit the loading treatment; authored fills remain unchanged. Ordinary manually created frames need no generation metadata.

The app-only `canvas_watch_project` tool uses ordinary `tools/call`, without a UI resource association. It waits at most ten seconds, waking on store notifications and atomic project-file changes from other processes. An unchanged heartbeat contains no project. A sequential watch loop renders newer snapshots for the bound project, ignores obsolete responses after navigation, and waits for local saves before applying remote state. Watch requests stop when hidden or unmounted. Hosts with an older runtime fall back to polling until reloaded; errors back off instead of creating a busy loop. Project summaries refresh on updates, focus, or a quiet interval.

The standalone endpoint is `GET /api/projects/:id/changes?afterRevision=N`, with the same JSON response and bearer-token support. Disconnects cancel the wait. The existing `/api/events` endpoint remains available to older clients.

This delivers saved design progress rather than unfinished tool arguments. Optional host partial-input messages are not required and never mutate a persisted document. Closely spaced saves can coalesce into the latest available snapshot. The pane does not replay snapshots with artificial delays, change the user's viewport, or make up completion percentages.

## Saved versions

Every save snapshots the application project, including every board, page, node, source field, shared token, and anchored conversation. Existing projects begin with their current saved state as a baseline; earlier edits are not reconstructed. Version metadata contains `revision`, `createdAt`, `label`, and optional `restoredFrom`.

`canvas_list_versions` and `canvas_get_version` are read-only and available to both the model and app. Historical reads return `historyPreview: true` in `structuredContent`. Clients must keep that result separate from live project state; the browser client's `projectFromResult` ignores flagged results. The dedicated `client.getVersion` validates and returns `{ project, version }` for the History preview. Read `canvas_get_project` again before making ordinary edits, rather than using a historical revision as `expectedRevision`.

History previews flash changed elements yellow without mutating the saved document. Restoring requires the user's explicit **Apply** action and affects the entire project across all boards. `canvas_restore_version` is app-only through `_meta.ui.visibility: ["app"]`, with the ChatGPT compatibility fields `openai/widgetAccessible: true` and `openai/visibility: "private"`. It is not exposed to the model. Models may inspect history for context; they should leave restoration to History's Apply action and must not bypass it by replacing the live document through edit operations.

Apply checks `expectedRevision`, preserves all saved versions, and saves the selected snapshot's content as a new current revision. Revision numbers continue increasing. A concurrent save rejects a stale Apply with `revision_conflict`.

The browser client uses `listVersions(id)`, `getVersion(id, revision)`, and `restoreVersion(id, expectedRevision, revision)` for both transports. Standalone REST routes are `GET /api/projects/:id/history`, `GET /api/projects/:id/history/:revision`, and `POST /api/projects/:id/history/restore` with `{ expectedRevision, revision }`.

## Export scope

Without scope IDs, `canvas_export_project` includes every board. `boardId` selects one board, `pageId` selects one page, and `pageId` plus `nodeIds` selects subtrees. A page must belong to the supplied board. Application identity, revision and shared tokens remain available. A scoped selection document retains ancestor shells with frozen positions so omitted siblings do not reflow it; `original-scope.json` retains the original scoped layout/source. Export never changes the saved design.

The default remains page HTML with `pageId` and a source bundle otherwise. Explicit `format: source` returns editable JSON, HTML previews and handoff notes, with React/CSS also supplied for a selection. `format: react` or `html` requires a selection or page. SVG accepts only one self-contained passive leaf SVG source layer without container styling. Source using CSS variables stays in the sandboxed document renderer for canvas, HTML and React so its project token definitions remain available; standalone SVG export is disabled with a format explanation. React supplies fixed design geometry and controlled shader rendering; application behavior still needs implementation. Arbitrary code stays script-free and network-blocked in sandboxed iframes.

Media bytes stay outside model responses: `assets` provides metadata and `assetPaths` maps output paths to references. Read binary chunks separately when saving a portable handoff. The browser Export panel builds media-inclusive source ZIPs and editable backups for any scope, including per-page React/CSS for board/project source archives. Import its unmodified, uncompressed ZIP through the project menu to create a new project. Compressed/repacked archives are unsupported. The archive limit is 256 MiB. Native instance links and current definitions persist in editable JSON; partial selection exports detach incomplete instance maps. Import rebases current releases into the new history baseline and detaches outdated instances whose release snapshots are absent, preserving their native appearance and conversations.

## Media and shaders

Image/video nodes reference `media.src: asset:<64 lowercase SHA-256 hex characters>`; optional image posters use the same reference format. Files are bounded to 32 MiB each, with at most 1 MiB raw bytes per upload/read chunk. Accepted types are PNG, JPEG, WebP, GIF, passive SVG, MP4, WebM and QuickTime; codecs still depend on the browser. Metadata, offsets, signatures, base64 and checksums are validated. No remote URL fetching or arbitrary file access is provided.

Binary storage lives under `assets/` outside project JSON and history. Identical content is deduplicated; binaries remain available for saved versions. Normal project/transaction limits stay 2 MiB. Completed assets must exist and match media type before a project write/import/restore succeeds. Upload state expires after one hour; at most eight pending uploads are allowed. REST routes under `/api/assets` use existing authentication and return metadata or JSON byte chunks, never a navigable media endpoint. The browser creates reference-counted Blob URLs and releases them when no longer needed.

`canvas_cancel_asset_upload` and `POST /api/assets/uploads/:uploadId/cancel` remove only an incomplete upload directory under the existing shared write lock. They validate the UUID/path and return `cancelled: false` if it is missing or already completed; completed asset references and saved versions remain available. Cancellation does not change project revisions or navigate the canvas. The client stops before another chunk, aborts HTTP chunk requests where possible, and attempts pending cleanup after failure or cancellation. It deliberately waits for the begin response to learn the upload ID. An already-running MCP call or final server write may finish first. Cleanup is best effort if the host disconnects or lacks the new tool; the existing one-hour expiry remains the fallback. Resumable uploads and completed-asset deletion are not provided.

During canvas imports the toolbar's Insert control becomes Cancel, including in narrow panes where save status is hidden. Inspector file/poster replacement has its own Cancel control. Switching project/page, opening History or unmounting aborts an active import; Inspector selection changes also stop replacement. Cancellation preserves already-added files and does not undo a design save already in progress. A replacement is applied only after a complete upload and a current-target/abort check.

Shader settings select `mesh`, `waves`, `grain` or custom GLSL. Uniforms are `u_resolution` (vec2), `u_time`, `u_scale`, `u_seed` (floats), and `u_color1` through `u_color4` (vec4). Static is the default. The controlled WebGL renderer bounds resolution and animation cadence, pauses offscreen/background, respects reduced motion, and releases GPU resources. Design JavaScript is never executed. Inspector controls cover fit, alt text, playback, colors, scale, seed, speed, animation and fragment source.

## UI resource

`ui://codex-design/canvas-v2.html` returns the compiled app as `text/html;profile=mcp-app`. It declares standard `_meta.ui` resource association and CSP fields. Media requires only the `blob:` resource scheme; `connectDomains` remains empty. Its `_meta["openai/ui"]` advertises `availableDisplayModes: ["inline", "fullscreen"]` and `preferredDisplayMode: "fullscreen"`. The latter requests the desktop host's content-pane presentation when the model opens the canvas; it is not an OS/browser fullscreen request. The host controls the final layout. The `canvas_open_canvas` thread launcher and app-only `canvas_open_app` global launcher associate with the resource; ordinary edits return data without repeatedly mounting the editor. Their separate `_meta["openai/ui"].entrypoints` keep the sidebar project browser distinct from each conversation’s canvas. Fresh design requests use the skill's open-before-edit workflow even when the editor was closed.

The app uses the MCP Apps `ui/initialize`, `ui/notifications/tool-result`, `tools/call`, and `ui/message` bridge over `postMessage`. Initialization advertises both `inline` and `fullscreen`; the app preserves the initial mode selected by the host and does not send `ui/request-display-mode`. It feature-detects the corresponding `window.openai` helpers for ChatGPT compatibility. Standalone browser operation uses the local HTTP API. The installed widget inlines its JavaScript and CSS and needs neither a CDN nor a local web server to render.

## Conversation selection

Embedded startup waits for bridge initialization and launch data before selecting a project. Explicit tool-input IDs take precedence over restored `hostContext["openai/modelContext"].structuredContent`, with widget state as a compatibility fallback. Scoped launcher output can supply a server-restored selection. An unbound pane shows the project menu; it never loads the globally most recent project or creates an untitled project automatically. Standalone browser URLs keep their explicit project/board selection behavior.

Each launcher result carries a fresh `canvasLaunchId`. The pane retains this launch marker and its scope with its context so remounting an old invocation restores a later manual selection, while a new explicit open can choose a new target. The thread launcher also reports `canvasTargetExplicit` so the UI can distinguish explicit target arguments from a restore request even if host input/result notifications arrive in different orders. These markers describe an application launch request, not a host tab or conversation.

Selection changes publish project, board and page IDs through `ui/update-model-context`. App-only `canvas_set_selection` also stores a validated preference when tool-call metadata includes the host's documented `openai/session` conversation ID. The storage key is a SHA-256 digest scoped with the optional host subject and organization; raw conversation identifiers are not persisted. SDK transport session IDs are not chat identities and are not used. A host without conversation metadata relies on attached app context/widget state. Missing, corrupt or stale preferences do not select another project. Preference files live in `.canvas-selections/`, outside project documents, project listing and saved history.

The active pane also publishes `selectedNodes`, an array of `{ id, name, type }` for its current object selection. The backward-compatible `selectedNode` is populated only for a single selected object and is null for groups. Object selection remains pane-local; it does not create design revisions or broaden project scope. Use those IDs with existing component reads and revision-checked batched `canvas_edit_project` operations. The UI's selection export/handoff includes every selected ID.

An open pane accepts live document updates only for its selected project. Cross-project reads, another pane’s launches, and creating a board do not redirect it. Explicit menu selections switch that pane and update its context. A new launcher invocation can navigate its associated pane only after matching explicit tool input with a scoped launch result; ordinary project results cannot navigate. Historical previews never replace its persistent live selection.

An anchored thread is queued before a follow-up is sent to the host. If a host follow-up fails, the queued request remains available to `canvas_get_pending_comments`. An ordinary browser has no authority to start a Codex conversation; the user supplies its prompt to an active connected agent. The server does not synthesize assistant replies.

## Generated images in component comments

The comment composer's Image toggle persists optional `intent: "generate_image"` on that user message without changing its text. Older comments remain valid. The shared follow-up prompt includes project/board/page/node/thread IDs and selected dimensions, then asks the active agent to read current image-placement context, use the native image tool, import the actual result, reread the current revision and place it through `canvas_edit_project` before replying. Queued image requests expose the same prompt in their optional `request` field. Ordinary natural-language image requests also use this workflow; explicit intent is a convenience rather than a requirement.

`canvas_get_node_context` defaults to its existing response. With `includeImagePlacement: true`, `imagePlacement` includes the selected node's stored, resolved-local and absolute boxes, aspect ratio, source/lock/hidden flags, parent stack constraints, up to ten structural image-slot candidates and up to ten direct children of the nearest usable container. Truncation flags identify bounded lists. These are placement hints, not a semantic decision or an automatic whole-frame fill. The agent reads relevant source/ancestors, preserves editable text/controls and source, and chooses an appropriate explicit image box or replaces an existing image reference.

`canvas_import_generated_image` is model-only and registered only by the local stdio entry. Its absolute `filePath` must stay strictly within the configured `CODEX_HOME/generated_images` directory (default `~/.codex/generated_images`). It rejects URLs, traversal, symlink descendants, nonregular files, unsupported raster signatures, files over 32 MiB and detected file/path changes during the bounded read. It copies PNG/JPEG/WebP bytes through the existing validated asset upload pipeline and returns `{ asset }`, retaining originals and completed assets. It does not generate, place, navigate or mutate a project. HTTP MCP, REST and the embedded app do not expose this local-file importer; other environments use the existing generated-byte upload tools.

Directory membership cannot prove which program produced a file, raster signatures do not establish complete decodability, and Node's public filesystem API does not provide atomic multi-component `openat` traversal against a hostile same-user directory replacement. Native generation itself depends on the active host's available tools. There is no plugin model API call, provider configuration, API key requirement or simulated successful generation. Errors must be reported honestly; placement and replies use the real saved revision.

## Versioned component library and canvas maps

The title-bar Design system entry contains Design system, Components and board-specific Inspiration tabs. Definitions in `designSystem.components` store stable identity, name/description, native node tree, root ID and released project revision. Each instance materializes native editable nodes with root-only `componentInstance` metadata: definition ID, version, definition-to-canvas node map and per-property overrides. Ordinary rendering, source, comments, media and layout keep their existing paths.

Atomic `canvas_edit_project` operations include `capture_component {pageId,nodeId,componentId,name,description?}`, `instantiate_component {componentId,pageId,nodeId,x,y,parentId?}`, `release_component {pageId,nodeId,label?,componentId?}`, `update_component_instance {pageId,nodeId,resetOverrides?}`, `detach_component_instance {pageId,nodeId}`, and `release_design_system {label}`. Instance root placement survives updates; local overrides are retained unless the caller explicitly resets them. Removal of a commented or overridden member rejects updating. Detach before hierarchy changes; nested instances are unsupported. Capture/release preserves passive source and token bindings, never runs corporate JavaScript.

Scoped version APIs share the existing immutable journal, with scope metadata in new version records and content comparison for older snapshots. Named system releases record checkpoints even when content is unchanged. History reads do not change the live project. Only app-only Apply can restore a scope: system restore preserves unrelated pages/conversations and freezes removed token bindings; component restore creates a new definition release without fleet updates. A system version that lacks a still-linked live component cannot be applied until those instances are detached. No literal Git repository integration, branches or merges are implied.

`format: svg-map` accepts `map: {background?: transparent|white|dark|#hex, scale?: 1|2|3|4, labels?: boolean, margin?: number}`. Frames/free objects keep their spatial arrangement, including negative coordinates; independent pages get separately labeled groups. The editor also captures PNG, with explicit output pixels and bounds of 16,384 per side and 64,000,000 total pixels. These are resolution limits, not measured peak-memory usage or print-DPI metadata. Browser SVG maps retain CSS/foreignObject and use embedded source/media/shader stills. MCP SVG maps keep passive source/shader content with explicit rendering warnings when browser snapshots are unavailable. Vector-tool compatibility and live CSS font matching depend on the consumer. Exports do not modify designs.
